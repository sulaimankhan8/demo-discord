## System Behavior

* Message ordering preserved (Snowflake IDs)
* No duplicate messages detected
* No message loss at application level
* Backpressure engaged correctly under burst load
* WAL buffering prevented uncontrolled memory growth
* Batched ACKs reduced socket write amplification
* WebSocket-only transport prevented polling amplification
* Failure mode dominated by connection saturation rather than DB limits
* System remained stable with deterministic degradation

## Bottlenecks Identified

1. WebSocket connection fan-out limits per instance
2. Node.js event loop contention under burst emit traffic
3. Socket.IO per-client overhead
4. Lack of horizontal scaling layer (Redis adapter)
5. Single-instance WebSocket scalability ceiling

## Capacity Conclusion

Safe operating range:

* ~170–220 messages/sec sustained
* ~120–160 concurrent active WebSocket users

Degradation zone:

* ~220–300 messages/sec
* Increasing WebSocket disconnect rate with stable latency

Overload zone:

* > 300 messages/sec
* WebSocket disconnects dominate
* ~50% virtual user failure
* System remains alive and responsive

## Verdict

Attempt 35 confirms that the system remains stable under moderate load and degrades predictably under burst stress.

Compared with Attempt 34, the system processed significantly more total messages with a lower failure percentage while maintaining very low latency.

The WebSocket-only transport continues to eliminate polling amplification effects and produces a cleaner and more deterministic saturation behavior.

The remaining limits are primarily due to the inherent fan-out constraints of a single Socket.IO instance and Node.js event-loop capacity rather than application logic, message persistence, or protocol correctness.

Further scalability improvements will require horizontal scaling mechanisms such as Redis-based Socket.IO adapters, distributed message fan-out, or multi-instance sharding.
