# Bottlenecks Identified

1. WebSocket connection fan-out limits per instance
2. Node.js single-thread event loop contention under burst load
3. Socket.IO per-client memory and transport overhead
4. Lack of horizontal scaling layer (Redis adapter)
5. Single-node infrastructure limits (CPU credits and network throughput)

# Verdict

Attempt 36 demonstrates measurable improvements compared with earlier runs. The system processed the highest total message volume observed so far while maintaining very low latency and significantly reducing timeout failures.

Compared with Attempt 34 and Attempt 35, the application handled more messages and a higher percentage of successful virtual users while keeping event-loop latency extremely low.

The WebSocket-only transport continues to eliminate polling amplification effects and provides a predictable failure mode dominated by connection saturation rather than application or database errors.

The remaining scalability limits stem primarily from the intrinsic fan-out constraints of a single Socket.IO instance running on a small compute instance rather than from message processing, persistence logic, or protocol behavior.

Further scaling will require horizontal distribution mechanisms such as Redis-based Socket.IO adapters, multi-instance gateway sharding, or distributed WebSocket fan-out.
